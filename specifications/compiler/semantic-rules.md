# Compiler candidate 0.1 — semantic rules

These policies define the CORE-18 semantic contract and remain revisable through evidence. An initial subset now has implementation and tests; the [coverage inventory](../acceptance/coverage.json) and [implementation evidence](../../docs/implementation-evidence.md) identify its limits. The grammar decides which forms can be read; these rules decide whether supported forms describe a coherent contract. Relationships are derived from declared uses; no separate notation is required.

## Names, scopes, and supplied dependencies

- Use decoded, case-sensitive names and qualified segments from the source model. No spelling correction, case folding, implicit declaration creation, or lookup into an actual project occurs.
- Each module/concept/type/helper/scenario/interaction establishes the relevant lexical scope. Declaration names in one scope must be unique; lookup also checks that the declaration has the required kind. A type named `saveGame` cannot satisfy a public capability reference.
- Top-level declarations, concept members, helper declarations, and fixture declarations can be referred to before their written declaration. Parameters, let values, scenario captures, and interaction captures become available only after introduction. Generic parameters are available within their declaring type.
- The candidate has one name namespace per scope, with kind checks for each usage. Nested scopes may shadow nonbuiltin outer names; they cannot shadow builtins. A duplicate parameter/local/capture within the same scope is rejected. Different concepts may independently declare the same member name.
- Builtin names Text/Number/Boolean/List/Nothing are language-supplied. They require no `use` or `depends on`, and source declarations/import aliases may not replace them. URL and arbitrary names such as PlayerStateSnapshot are not automatically available.
- A `use` introduces only its selected export under the written name or alias. A unique catalog locator and exported symbol must be available. Two imports introducing the same spelling from different declarations produce ambiguity. An import alias colliding with a local declaration is a duplicate. Repeating the same introduced name is also a duplicate, not silent merging.
- A dependency catalog is closed typed metadata, not arbitrary strings. IDs referenced by signatures, fields, members, exports, and type shapes must exist. The caller assigns catalog IDs uniquely within the snapshot. The compiler may remap them into its result IDs while preserving declaration identity/provenance; aliases do not clone declarations.
- `depends on X` must identify an available concept-like or type declaration. It supplies a dependency edge, not a declaration/import, ordered message, or proof that an implementation exists. A package requirement must match an available configured alias and any specified phase.
- Local types/concepts are visible inside their owning concept and descendants. Referring to them through qualification outside that owner fails accessibility. Public capability signatures—including nested generic arguments and aliases—must not expose local types. There is no implicit promotion to an exported type.
- Each `public` entry must name exactly one capability declared for that owner. Duplicate entries fail. Capabilities without public references remain nonpublic. External calls or interaction messages into another concept require a public capability; internal calls can use the owner's own members. Examples attached to a subject share its example/subject scope, preserving the intended equivalence of inline and composed examples.
- Multiple construction declarations for one concept are rejected. Construction parameters are independent of operation parameters. Construction values are not implicit variables in every capability contract.

## Type meaning and compatibility

- Text, Number, and Boolean are distinct scalar types. Literal types are subtypes of their respective scalar types and match their exact value. Numeric literal equality uses exact finite decimal meaning (so `1` and `1.0` denote the same numeric literal value); the source model preserves their spelling. Type checking does not evaluate arithmetic or choose a target's numeric storage representation.
- Record, opaque, and concept-like declarations have nominal identity: different declarations do not become the same type because their fields happen to match. Transparent aliases expand to their target type while retaining the alias declaration and provenance. Opaque types have no assumed fields or implicit conversions.
- Reject cycles consisting only of transparent alias expansion, including generic self-expansion. Recursive references through record fields are allowed; dependency cycles are not automatically alias cycles. Helper recursion may be type-correct but does not prove termination or execution success.
- A generic application must have the declared number of arguments. Type parameters are scoped references, not new global types. Named generic applications are invariant: the same nominal declaration requires equivalent arguments. Typechecking a supplied record/list literal against an expected type is a separate operation from converting an already typed generic value.
- List<T> represents an ordered homogeneous collection. Tuples have fixed length and ordered element types. Bracketed literals are context-checked as a list or tuple; a list value does not silently convert into a tuple. Without a required type context, a nonempty bracket literal gets List of the union of its element types; an empty bracket literal needs an expected list/tuple type.
- A source value is assignable to a union if it fits at least one alternative. Every alternative of a source union must fit the destination. Union ordering remains authored source information but does not change assignability. An optional type accepts a present compatible value or absence; an optional value cannot flow to a required value without a declared operation that supplies one.
- Optionality allows omission of a field. It does not add an undeclared `null`/`nothing` literal, make any parameter optional automatically, or make arbitrary member access safe. Parameters may be omitted only when a default is declared; their type can independently be optional.
- An anonymous record literal requires an expected declared record type, or a union where exactly one record type fits. A typed record identifies its intended nominal declaration. Reject unknown fields, duplicate entries, incompatible values, and missing required fields unless an optional field or default permits omission. Do not invent missing field data. A typed record of one declaration is not assignable to another nominal record.
- Named record fields and their defaults are checked in their declaration's scope. Field defaults cannot access an instance or sibling fields. Fixture expressions may refer to other fixtures or declarations in scope; fixture/default value-dependency cycles fail. Parameter defaults may refer to earlier parameters and available fixtures, but not later parameters or the eventual `result`. Validate all defaults without executing them.
- Nothing is allowed as an explicit callable return type only. It is not a usable field/parameter/generic argument value type and cannot be captured or passed as a value. An omitted return type means unspecified. Preserve it with an obligation; reject its use where a known value type is required. Never infer Nothing merely from omission.
- Arithmetic operators require Number-compatible operands and produce Number. Ordering comparisons require numbers. Boolean operators and `not` require Boolean. Equality requires compatible comparable values: scalars, tuples/lists, and declared records are value-comparable; their execution uses value/structural equality, not target-language object-reference equality. Opaque/concept-like values require a declared comparison operation rather than invented equality semantics. These are typing/execution-contract rules, not a claim that expressions were evaluated during compilation.
- Type references, namespaces, and callable names used as call targets are not fabricated ordinary values. The candidate does not introduce first-class function types or arbitrary coercions. Member access checks the receiver's known fields/members and their accessibility; there is no implicit optional-value unwrapping or list indexing syntax.

## Signatures, contracts, helpers, and data flow

- Preserve parameter order and require positional argument count/type compatibility. Omitted trailing parameters need defaults. A required parameter following a defaulted one is rejected in this candidate. Duplicate parameter names fail. A record/list literal can use a parameter's expected type as its context.
- A capability/function declaration describes a contract, not a host-language implementation. Its preconditions and postconditions must be Boolean. Prose `promises` clauses remain separate obligations. A bodyless declaration is valid when its references/types are valid.
- `result` is introduced only inside ensures for an explicitly declared, value-producing result type. It is absent in requires, defaults, and bodyless/unspecified/Nothing result contexts. A parameter named result in such a contract conflicts with the contextual declaration. A result symbol is represented with ContextOrigin, never as an invented authored NameNode.
- A provided setup/action/observation body is checked in order. Let initializers resolve before the new name enters scope. Do calls must be callable and well typed. A return expression must fit the declared return type, and a value-returning supplied body must reach a final return. No statements may follow return. An empty provided body is allowed for explicit Nothing, but not as an implemented value-returning helper. Omitted bodies remain implementation obligations.
- A check has assertion semantics rather than a return value. A bodyless check is valid with `check-implementation-needed`. A supplied check body must contain at least one assert, and each asserted expression must be Boolean. Return statements in a check are rejected; a check call cannot be captured, used as a numeric value, or smuggled into a Boolean/arithmetic expression.
- Observation declarations name operations intended to observe state; compiler type checking does not prove that their eventual driver is free of side effects. A declared read-only intention is not evidence about implementation. Tests must observe the real system rather than helper-owned bookkeeping.
- A scenario's given steps call setup helpers, available functions, or subject capabilities; when steps call actions, available functions, or subject capabilities. Observation/check helpers cannot masquerade as action steps. Then contains a Boolean condition, a check call, or explicit prose. Calls inside conditions must produce compatible values.
- Scenario captures and let values are available only to subsequent statements/steps in the same scenario/body. They do not escape to another scenario, helper, or fixture. Capture cannot receive Nothing, a check, or an unspecified result. Duplicate captures fail. Reusable setup defaults and supplied arguments undergo the same checks as other calls.
- A short example checks that the actual and expected expressions have compatible value types; it preserves the expected expression independently of the actual expression. A prose expectation remains an obligation. No implementation, observed output, or passing assertion is inferred from the text.

## Interactions and composition boundaries

- An interaction's participant names are unique and refer to available concept-like types. Parameters are in interaction scope. Participants and captured replies must precede their use; the source grammar preserves interleaving so the validator can locate a bad order.
- Every message has an existing sender and receiver participant. Its recipient operation must be a declared public capability of the receiver type. Validate positional arguments against that signature. A reply capture obtains the declared result type; Nothing, a check-like result, or unspecified output cannot be captured.
- Preserve the exact message order, arguments, and captures. Do not infer reply messages or execution order from dependencies. Static consistency is not evidence that a running system sends those messages.
- Inline examples and same-document `examples for Subject` resolve their subject and share its logical example scope. An ownerless examples block can contain self-contained fixtures/functions-in-scope/scenarios; a source read does not invent an owner. A later external attachment can supply the owner during composition.
- include, extend, and external examples attachment are faithfully represented by the reader but rejected by the CORE-18 entry point with composition-required until the later composition work supplies a validated expansion. No declarations from these forms become available by accident. The compiler does not treat absent loaded content as an empty, successful contribution.
- Derive relationships from explicit dependencies, construction parameters, capability/function inputs and outputs, and typed fields. Preserve the owner, target, precise use, source location, and input/output/reference direction. Input means target enters owner; output means owner supplies target. References do not imply ownership, lifetime, runtime calls, or message order. No relationship keyword is introduced.

## Learning and test expectations

These choices are sufficiently explicit to implement and challenge. Examples should pair successful and unsuccessful inputs: a declared/missing type, compatible/incompatible argument, available/unavailable export, legal/illegal capture, and unfinished/ill-typed helper. Tests should identify what matters to the consumer and leave representation construction algorithms free.

Ready does not establish that these policies are ideal or implemented. If, for example, nominal types or strict default ordering obstruct a useful author scenario, preserve the counterexample, revisit the rule deliberately, and update the affected acceptance cases. Do not weaken a failing expectation solely to make current code appear correct.
